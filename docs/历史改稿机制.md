# 历史改稿：改的是一条有来源的故事历史

假设第3章把丹药交给甲，第8章又由甲交给乙。现在作者把第3章改成“没有交出”。系统需要重新核对后面的药物归属、人物知情和剧情，不能只替换一个Markdown文件。

## 从改稿到定稿

1. **先写草稿**。编辑历史章节只改变草稿，旧定稿仍保留在版本历史。旧审核和记忆提案失效，不能拿改稿前的勾选直接覆盖新正文。
2. **回到该章之前**。重新生成或审核时，读取前一有效章节的完整记忆快照；第一章使用初始记忆。检索只允许同作品、当前有效版本、位置早于本章的来源，后文和失效稿不能倒灌成“角色当时知道”的信息。
3. **重新提出变化**。正文经编辑审核后，系统提出新的摘要、事实、十份记忆变化和结构化事件。作者按新稿逐项接受或拒绝，程序绑定来源章、定稿版本和章内顺序。引文存在不代表解释正确。
4. **一起提交并使后续失效**。确认时，用SQLite事务提交正文、记忆、事实、选中事件和新版本；从本章开始的旧事实、检索块和事件标为失效，后续定稿章标为“待复核”。旧文本和旧版本仍在，不自动删除或覆盖后续正文。
5. **顺序复核后文**。从最早的待复核章节向后处理。作者可以保留正文重新审核，也可以修订。确认后建立新的来源版本，逐步恢复后续可用状态。

如果第8章还写着转交那枚已不存在的丹药，结构化事件回放会提示余额或来源前置条件不成立；模型编辑也可以指出原文冲突。程序不会替作者决定是修改第3章还是第8章，更不能保证模型找出所有文学因果问题。

## 草稿、正式状态与恢复版本的区别

未确认草稿不进入正式检索或账本。已经失效的后文仍可阅读，但不作为可靠历史证据。恢复某个旧版本，是把旧正文和标题复制到草稿，之后仍需重新审核、确认；它不是把整个故事数据库瞬间倒回旧时间。

正文和记忆事务先完成，FTS、向量及Markdown镜像属于派生物。恢复任务依提交回执避免多建一个正式版本，并重建派生资料。当前正式强杀测试覆盖FTS，没有声称覆盖向量故障或供应商扣费对账。ZIP保存有效定稿与事件，导入到新作品时来源ID不同，事件先成为待确认队列；完整失效历史需要SQLite备份。

## 可核对的实现

- `Repository.save_draft / restore`：草稿版本和审核失效。
- `Retrieval.context`：历史记忆快照；`Retrieval.search`：先限定合法来源再召回。
- `Repository.commit_chapter`：联合事务、旧来源失效、后续待复核。
- `story_state.replay`：依据当前来源版本和时间边界回放事件。
- [四种真实强杀的原始回执](../artifacts/resume/recovery/6cc76947e809412c9831fa0c4e8a12b7/results.json)：每案最终7条新事件有效、7条旧事件失效，重复确认不增事件和版本。这是离线工程夹具，不是文学正确率。
