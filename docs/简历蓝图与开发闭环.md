# 长卷项目简历蓝图与开发闭环

目标岗位是 Agent 应用开发与 Harness 工程实习。项目围绕一个具体问题展开：长篇续写和历史改稿时，如何把正确的故事状态交给模型，并让生成、审阅、记忆更新和恢复形成可靠闭环。简历最终突出能解释取舍、能演示、能追溯结果的贡献。

依据为用户提供的[调研原文](../artifacts/resume/research/用户提供的调研.txt)。其中混合检索、工具、记忆、评测、可靠执行和 AI 辅助开发均进入能力检查；“几乎必问”“必须有某个条数”的说法没有调查出处，不作为市场事实。下列指标是本项目验收目标，不能在实验前写成成绩。

## 合格门槛

以下检查共同决定项目是否达到本轮简历标准。不能用测试数量、技术名词数量或漂亮界面替代其中一项。

1. **具体问题与个人工作边界**：四个方向都能对应实际用户操作、改动代码和一个失败案例。标明本地个人项目与 Codex 辅助实现，不虚构企业、线上用户或独立人工研发经历。
2. **检索证据**：验收情境在开发前冻结，按情境划分而非将同一事实的改写查询拆到两边；单列未来候选挤占、版本与跨作品约束。合法历史召回、无答案误检与泄漏均有原始逐项记录；修复必须在已复现坏例上成立。总体未获益的配置不能写成普遍提升。
3. **上下文证据**：不可变原始记忆与模型视图区分；必需资料不能静默截断；超限有明确错误和裁剪审计。硬上限使用可核验的序列化字节，token估算及供应商实际用量另记；上下文子包预算不冒充完整请求token上限。
4. **工具与故事状态证据**：至少一组真实工具任务覆盖查询、证据使用与提案；无权限或过期参数不能落正式状态。资源和知情等结构化状态应有明确操作语义、来源与可回放验收，不能用“引文存在”替代语义正确。
5. **恢复证据**：至少覆盖真实子进程强杀、重复确认与提交后索引故障，验证最终正文、记忆、版本、检索和费用；不能只检查任务状态字符串。
6. **创作闭环证据**：新增机制经实际产品生成或修订新稿件，保存计划、工具轨迹、审阅、作者确认、状态与导出；至少一个既有叙事坏例得到按事先标准核验的改进。局部改善与整卷文学优势分别表述。
7. **简历可读与可追问**：一句简介和约四条贡献；每条包含问题、关键设计和有范围的结果。提供15–30分钟面试材料，能解释替代方案、失败及下一步。独立复审若发现过度表述或实质缺口，回到开发而不以改措辞放行。

## 第一轮判断与实施顺序

2026年10月21日初审：**尚不合格**。已有12章约3万汉字样书、事务提交和可恢复流程，但核心缺口是检索收益未单独度量、上下文没有预算、自由文本事实缺少确定操作语义，以及缺乏进程级故障与新增叙事改善证据。

先冻结当前四份核心模块并复现候选挤占问题；实现检索过滤和预算视图，建立独立数据与逐项结果。随后补故事事件与伏笔承诺的可回放语义、受限工具任务和故障恢复实验，再用新稿件验证。每轮保存“原问题→实现→结果→简历可写内容→尚欠内容”，未通过的项目继续保留在下一轮。

现有整卷、机制探针、压力输入和AI代理评阅保持原始结果，不用新实现覆盖旧实验。当前8/7/3的AI选择不能写成读者满意度提升；同样不能把合成千章测试或240条查询写成真实百万字创作和240个独立用户任务。

## 第三轮简历表达修订

用户反馈暴露了前轮表达审查的不足：第二条把故事状态、作者确认、工具协议和一次工具纠错测试混在一起，“DeepSeek工具任务经错误反馈修正”没有清楚的主语与修正对象，“五项提案”也不能解释系统价值。前轮工程证据成立，不代表文案已让首次阅读者理解贡献。

表达调整为五条，仍对应原四个开发方向：时序RAG与上下文管理、作者可控的设定更新、工具调用校验与纠错、中断恢复与幂等提交、有依据的编辑返工。作者确认、工具调用纠错和进程故障恢复分别组织证据；五条符合调研建议的4–5条范围，没有为了保留四条而把不同诉求合并。

门槛7增加以下实际检查：

1. 首句给出可想象的创作或运行问题，读者不必先理解协议和框架才知道用途。
2. 每条只承担一个核心主张，问题、机制和结果服务于同一主张。
3. 系统、工具、调用方Agent和作者的职责明确，修正对象具体到参数、引文或提案。
4. 专业术语解释设计深度；模型供应商、框架名和“真实调用”不能代替系统贡献。
5. 证据确实覆盖所声称能力。未执行作者确认的工具任务，不证明作者审阅和定稿闭环。
6. 数字说明单位、分母、比较对象和范围。夹具要求的“五项提案”不作为性能提升指标。
7. 保留小样本、主动注入错误、操作者干预及局部修复的边界，不包装成通用自愈或整体文学收益。
8. 简历正文保持可读篇幅，协议细节、完整指标和限制进入面试材料；详细材料须能支撑15–30分钟追问。

新版正文见[项目简历与面试材料](项目简历与面试材料.md)，两轮编辑检查、逐条证据对齐及未完成项见[第三轮表达review](../artifacts/resume/revisions/03/review.md)。本轮是同一实施AI的编辑自审，不是独立HR测读或招聘竞争力认证；仅修改文档，旧评审、封存交付与原始实验不覆盖。

## 第四轮 Agent 技术主线修订

2026年10月22日，用户进一步指出第三轮虽然拆清了功能，却弱化了Agent技术及其设计深度。这一反馈成立：把“中断恢复”“作者能拒绝变化”写清只是起点，还应说明Harness如何组织多角色长任务、长期记忆如何受控写入，以及工具、Skills和评测在整个系统中的职责。

本轮采用“朴素目的→Agent机制→实际复杂性→正式贡献→证据”的写作顺序。五条正式贡献调整为多角色Agent编排与Harness、上下文工程与时序RAG、HITL与长期记忆治理、MCP工具与领域Skills、Agent Evals与失败诊断。每条同时保留可理解的场景与可追问的技术决策。

| 原始要求 | 当前表达与实现对应 |
|---|---|
| 多Agent与Harness | 角色上下文隔离、结构化交接、双编辑并行、有限返工，以及检查点和业务幂等；准确说明是工作流编排，规划器才有独立工具循环 |
| RAG、记忆与上下文 | 合法来源先过滤、分层资料与角色预算；读取既有信息和写入新记忆分别讲清；保留检索策略比较及未获益配置 |
| MCP、Tool Use与Skills | 创作规范由Skill提供，工具提供动作，MCP提供外部调用契约；区分业务校验与客户端纠错，保留任务指导读取单一Skill的范围 |
| 评测与真实运行 | 冻结任务、记录尝试与轨迹、检查最终状态；12章样书、局部修复、整卷未优胜分别陈述，量化指标与实际测量单位一致 |
| AI辅助开发与可追问性 | 保留Codex辅助开发说明、实现入口和15—30分钟演示路线；不以技术术语或文案本身证明个人现场能力 |

门槛7在第三轮可读性规则上增加四项：

1. 每条要能用普通话说明“Agent在完成什么事”，同时保留对应的技术名称和实际设计；不能因追求易读而退化成功能清单。
2. 技术深度来自真实约束与决策，例如循环终止、检索资格、状态写入和恢复副作用。增加抽象形容词不能替代这些内容。
3. 先核对代码再选术语，区分框架能力、项目接入与实测结果。多角色编排不能改写为自主群体协作，读取单一Skill不能改写为多技能自主路由。
4. 同时做去术语检查与可追问检查：去掉技术名后仍能讲清用途；沿技术名追问时，能找到调用路径、控制条件、失败案例和证据。

当前文本与朴素解释见[项目简历与面试材料](项目简历与面试材料.md)，对正式成稿的审查见[第四轮表达review](../artifacts/resume/revisions/04/review.md)。本轮仅调整文档与表述，自审不能替代真实HR测读；已有实现、实验和前轮记录继续保留。
