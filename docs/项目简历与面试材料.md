# 长卷：项目简历与面试材料

## 可放入简历的版本

**长卷｜面向长篇小说作者的 Agent 创作工作台（个人项目，Codex辅助开发）**  
围绕长篇创作中的设定遗忘、改稿连锁影响和多轮任务中断，构建集多角色编排、分层记忆、工具调用与作者审阅于一体的本地 Agent 工作台，支持从故事规划到章节定稿的持续创作。

技术栈：LangGraph、DeepAgents、MCP；Python、FastAPI、SQLite；React、TypeScript。

- **多角色 Agent 编排与 Harness：** 基于LangGraph组织规划、写作、双编辑与记忆整理，隔离角色消息上下文、并行审阅，以原文证据驱动最多三轮返工；结合持久化检查点与幂等提交支持中断续跑，四类本地进程强杀测试中正文、记忆及版本均正确恢复，重复确认未新增版本。
- **上下文工程与时序 RAG：** 针对续写遗忘及旧稿、未来信息干扰，分层组织核心记忆、近期摘要与历史证据，在召回前按作品、章节时点和有效版本过滤，再按角色预算装配上下文；64问验收Recall@5为81.25%（原76.56%），另在72个角色视图离线重放中减少27.14%资料子包字节。
- **Human-in-the-loop 与长期记忆治理：** 将资源、角色知情与伏笔变化建模为带来源的可回放事件，经状态预检和作者逐项确认后与正文原子提交；以正文哈希、版本校验阻止过期提案写入，历史章重新定稿后使后续旧状态失效、后文待复核，让作者控制Agent记住什么。
- **MCP 工具与领域 Skills：** 为DeepAgents规划器接入按任务读取、可追踪版本的玄幻Skill；为外部Agent实现受限的故事查询与变更提案MCP服务，校验参数、版本和引文并反馈具体错误，供调用方Agent修正后重新调用；单次错引文注入任务验证了该反馈纠错链路。
- **Agent Evals 与失败诊断：** 以冻结任务、执行轨迹和最终状态建立分层评测，结合规则检查与匿名AI评阅核验返工成效；完成12章约2.98万汉字样书及对照，另在新稿单例中核验返工补齐动作因果缺环，同时保留篇幅恶化和新三章对照未获整体优势的结果。

## 五条贡献各自在解决什么事

**第一条：让Agent把一项多步骤工作持续做下去。** 一本小说需要反复规划、写作、检查、修改和记住结果。Harness在这里是管理这些步骤的执行层：每个角色拿到明确的输入，双编辑分别返回结构化意见，状态图决定继续修改还是交给作者。复杂性在角色交接、循环终止和中断后的副作用处理；检查点解决“做到哪一步”，事务与提交标识解决“这一步是否已经写入”。多角色分工和恢复共同服务于持续执行。

**第二条：让每次续写拿到此刻应该知道的资料。** 例如人物第五章才知道的秘密，不能提前用在第三章；前文废弃的设定，也不能继续被检索出来。上下文工程负责组合核心记忆、近期内容和相关原文，时序RAG负责筛选合法历史依据，预算控制负责在有限空间内选取完整资料。复杂性在检索资格、相关性和容量约束必须同时成立；角色视图的裁剪不会覆盖完整记忆。

**第三条：决定模型提出的哪些变化可以成为下一章的正式记忆。** 以“用掉一枚丹药”为例，模型先提出带原文来源的状态变化，程序检查已知数量等前提，作者再接受或拒绝。Human-in-the-loop（HITL，人在关键步骤确认）落实为可暂停的确认节点、逐项选择及受版本约束的提交。复杂性在正文、审核与记忆必须属于同一版本，历史章重新定稿还会使后续状态的依据失效；这比一个确认按钮多了完整的写入约束。

**第四条：给Agent提供创作规范和可执行的动作，并让失败反馈能被利用。** Skill告诉规划器如何考虑成长代价、战斗因果和伏笔；工具让它查询故事资料。面向外部客户端的MCP服务提供统一的查询与提案接口，应用校验请求，调用方Agent根据具体错误修正后重试。复杂性在知识加载、协议调用、业务权限和纠错循环各有职责；内部规划工具与外部MCP分别实现，当前Skill读取由任务指导。

**第五条：判断Agent究竟做成了什么，以及该改哪一处。** 资料检索要看有没有找到依据，工具任务要看调用和最终状态，文学返工还要对照原稿与改稿。例如原稿声称验证了“封堵导致停响”，却缺少解除后复响；核验就要检查这一步是否补齐。Agent Evals把这些检查分开，保留失败尝试。复杂性在区分局部修复、操作者干预与整卷效果；动作缺环补齐仍伴随篇幅恶化，不能推出小说整体更好看。

这五条分别对应执行、读取、写入、工具与技能、验证。正式简历保留技术名称和关键决策，面试时用上述场景解释，再展开代码和实验。

## 技术取舍与指标含义

检索验收中的Recall@5衡量前五条检索结果是否包含指定依据：默认关键词为52/64（81.25%），旧策略为49/64（76.56%），差异是3条查询。64问来自同设定两卷16章的32个事实，每事实两问；按章的探索性重采样区间包含零，不能称统计显著或广泛泛化。默认策略在开发集选定，验收后未改选。

关键词适合虚构专名与原句，向量用于近义线索，RRF融合及重排也实际比较过。该次验收中重排62/64，但本机热查询P95约9.03秒，未作为默认；关键词为7.694毫秒。另一组短构造档案中新融合91.67%低于原策略94.17%，保留了未获益结果。查询命中率不能当作小说事实正确率或文学评分。

上下文的27.14%只指24个已保存资料输入在三个角色视图中的离线子包字节变化；完整原始资料未被覆盖，必需项不能静默截断。该实验不包含历史作者指令，也没有测出完整请求token、实际费用或文学质量改善。

结构化账本检查已知余额、来源版本、角色知情和事件顺序；未知库存保持未知。自然语言含义仍可能被提取或审阅错：额外改稿中，正文已写两次触温、第三次被挡下，操作者却接受了“三次触温”的事件摘要。最后经记忆编辑器人工修正，正文版本1未变，旧审核失效；[勘误与新导出](../artifacts/resume/live-rewrite-v1/memory-correction-addendum.json)保留。作者确认是写入权限和编辑控制，不是语义准确性证明。

## 工具纠错与作者确认分别验证

工具纠错链路为：调用方Agent提出调用，适配器校验参数、作品、版本和引文，将错误码与原因交回调用方，Agent修正参数或提案后重新校验。固定任务事先要求故意提交错误引文；错误引用被拒后，模型给出正确引用，提案通过回放预检。它说明这一任务的错误反馈可以被模型利用，不代表所有错误均可自动修好。

这次验收的调用方客户端最多执行8次模型调用，并设置本地调用预算；MCP服务另外限制单次输入、输出、超时和调用频率。模型纠错循环由客户端驱动，服务端负责校验与错误反馈，两者不能混称为整个创作系统具有通用自愈能力。

该任务中的“五项待审变化”是夹具要求的验收目标，不是性能提升指标；任务未执行作者确认，因此“正式状态未变”只能作为没有越过写入边界的核验。作者审阅、拒绝及定稿的能力使用上表中的实际界面记录验证，不能由这个工具样例代替。

状态回放失败时可能保留标记无效的待审提案；调用超时也可能出现“提案已保存、结果未返回”，工具会提示重新核对版本。此时应先查明状态，不能把同样请求无限重试。MCP服务只提供查询和提案，没有正式定稿、任意文件或终端权限；[MCP与Skill边界](MCP与技能边界.md)记录完整契约和限制。

## 15—30分钟面试展开

**前2分钟，展示作者要做的事。** 打开一个章节，从目标、正文、编辑意见讲到待审记忆与定稿，说明作者为什么需要持续创作而非单段生成。用一句话概括五条主线：持续执行、取对资料、控制记忆写入、扩展工具与技能、验证结果。

**第3—7分钟，解释Agent如何把工作推进下去。** 展示状态图中的角色、结构化交接与双编辑并行，解释为什么生成正文顺序进行、审核失败最多再修订三轮。LangGraph保存执行位置，SQLite事务与run_commits处理恢复后的业务写入，FTS和Markdown是可重建派生物；用四种强杀回执展示恢复前后内容与版本。外层Harness由应用控制，规划器内部另有受步数约束的DeepAgents工具循环。

**第8—13分钟，解释为什么能取对资料。** 以“人物到第五章才知道的事，第三章不能引用”“作者已废弃的旧稿不能继续检索”为例，说明作品、时间和版本如何在召回前筛选；再解释450字切块、380字步长、重叠依据的any-of判定，以及关键词、BGE向量、RRF和重排的取舍。演示完整记忆与模型视图分离，说明预算为什么使用可复算的UTF-8字节，以及64问命中和72视图字节分别测量什么。

**第14—18分钟，解释谁决定正式记忆。** 展示库存未知的转移提案为何被阻止、作者如何取消该项后定稿；解释资源、知情和伏笔事件的来源与顺序。演示改稿使旧审阅失效、历史定稿修订使后文待复核，说明HITL与版本约束怎样共同阻止旧提案写入。接着展示事件摘要勘误，解释数值前置条件、作者确认和自然语言正确性之间的边界。

**第19—23分钟，解释工具与技能怎么进入Agent循环。** 从Skill文件内容、版本哈希和实际读取记录，讲到规划器的只读检索；再展示外部MCP错引文请求、错误码、调用方修正和复验结果。解释Function Calling、MCP与Skill各自职责，指出服务端负责校验，客户端驱动纠错，任务有步数与预算上限。Skill实际由任务指导读取一份玄幻规范，不能声称自主多技能路由或因果收益。

**第24—28分钟，展示评测怎样判断Agent的工作。** 区分冻结任务、一次尝试、工具及角色轨迹、最终正文与故事状态。对照同一场景首次语义审核前后稿：原稿只写封堵和停响，缺少解除后复响；改稿补齐动作，但篇幅从1627增到1990字符。再展示两组三章稿未通过期限、代价执行及篇幅条件，说明局部修复为什么不能替代整卷结论，以及程序检查、模型判断和阅读偏好分别能回答什么。

**最后，说明本人参与和AI协作。** 结合可演示的代码与真实参与记录，说明需求判断、验收规则、方案选择、代码审查和修复中本人实际做了什么。实现、操作与评阅都有Codex辅助，不把框架能力或AI代做内容写成独立手写研发经历。

## 高频追问与回答依据

- **多角色分别负责什么？** 规划员组织目标和场景，作者生成正文，一致性与叙事编辑分开检查，记忆整理员提出变化；编辑可并行，正文顺序生成。同一基础模型的不同上下文不构成统计独立判断。
- **Harness在这个项目里具体是什么？** 是围绕模型调用实现的执行控制：组织角色与数据交接、决定返工和暂停、持久化进度、预留费用、记录事件并处理恢复后的提交。LangGraph提供状态图与检查点，正文和记忆的事务、版本校验与提交幂等由业务层实现，不能把框架自带能力全算成项目自研。
- **哪些Agent实际调用工具？** 规划器使用DeepAgents工具循环及创作Skill；作者、编辑和记忆主链由应用编排。外部MCP客户端是另一条工具调用路径，不能把内部检索轨迹算成MCP调用。
- **读记忆和写记忆为什么分开讲？** 上下文工程回答“这次任务应看到哪些已有信息”，HITL与记忆治理回答“这次生成的新信息何时能被以后任务使用”。检索即使完全命中，也无法纠正之前被误写入的事实，因此读取资格和写入许可需要分别设计。
- **为什么不是直接调用函数？** 内部工作流用函数调用更简单；MCP将相同的资料查询与提案契约提供给其他客户端，作品范围与写入权限仍由应用校验。
- **是否证明小说更好看？** 12章样书证明全流程运行过；局部返工证明一处动作缺环被补齐。旧样书AI片段选择为完整工作流8、旧策略7、接近3，新三章对照两组均未通过验收；没有整体文学优势或真人追读提升证据。
- **为什么不默认启用所有先进技术？** 实测中融合不总获益，重排更准但慢；额外编辑增加调用和返工成本。采用实际有依据的默认策略，把其他能力留为可选。
- **怎样证明个人能力？** 本项目是Codex辅助个人项目。简历使用者需要能现场解释、复现失败并修改相关代码；材料本身不认证本人已经具备这些能力。

## 项目与验证范围

目标岗位为Agent应用开发或Harness工程实习。模型配置为DeepSeek官方API的`deepseek-flash`，调用日期、实际返回标识和用量保留在实验记录；模型供应商不作为系统纠错能力的贡献主体。费用为本地估算，不是供应商账单对账。

现有证据覆盖单人本地产品、工程夹具、实际模型运行、AI操作者与AI评阅。没有企业或付费用户经历，没有真人盲评投票，也没有多作者长期使用、百万字效果、Skill因果收益、云生产SLA或通用自愈能力的验证。上述边界限制各项结论，不能用测试数量代替用户价值。
